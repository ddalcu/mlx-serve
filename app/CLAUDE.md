# Swift macOS app (MLX Core) — AI context

Compressed rules. Full war stories: `../docs/gotchas/app.md`. Full service contracts: `../docs/reference.md`. Repo-wide policy (TDD, release, conventions): root `../CLAUDE.md`.

## Build

- ALWAYS ship via `bash app/build.sh` (signs, entitlements, links Zig artifacts, keeps MLXCore + mlx-serve in lockstep); dev: `SKIP_NOTARIZE=1`. **No signing identity on the machine?** `APPLE_DEVELOPER_ID='-' APPLE_TEAM_ID='-' SKIP_NOTARIZE=1 bash app/build.sh` takes the ad-hoc branch (line 282: hardened runtime and productbuild are skipped for `-`), which is how a dev bundle is already signed — `codesign -dv` on it reports `Signature=adhoc`, `TeamIdentifier=not set`. A release still needs the real identity, so cut it where that lives or via `.github/workflows/release.yml`. Swift-only fast iteration escape hatch: `cd app && swift build -c release`. Never force a global Swift language mode through SwiftPM: MLXCore's manifest keeps the app in Swift 5 mode while modern dependencies compile in the mode declared by their own manifests (swift-sdk must stay >= 0.12.1; 0.10.x cannot compile in the MAS Xcode project).
- **`FAST_DEV=1 bash app/build.sh` is the iteration build, and an UNSET var is the release path byte for byte** — one variable gates every shortcut, so a shipping build can never take one by accident. What it changes: Swift compiles `-c debug` (the single biggest lever — `-c release` turns on WMO, so touching one file recompiles the module, and SwiftUI's type-checker is what makes that minutes; the two configurations keep SEPARATE build dirs, so alternating costs a full rebuild of whichever you left); CalVer skips the `gh` round-trip and does NOT stamp the tracked Info.plist (a fast build cuts no release, and a dirty tree is what breaks release.yml's Homebrew rebase); the bundle is updated IN PLACE (no `rm -rf`) and the icon is regenerated only when the bundle has none; the frameworks are re-staged, re-fixed-up and re-signed as ONE decision, skipped while `lib/mlx/lib/libmlxc.dylib` is no newer than the bundled copy — `install_name_tool` rewrites a file and invalidates its signature, so skipping the re-sign while still running the fixups would leave broken signatures in the bundle; and it stops at a signed .app, before notarization, `productbuild` and the DMG. What it deliberately does NOT change: **mlx-serve stays `-Doptimize=ReleaseFast` even under FAST_DEV** — Zig's cache already makes an unchanged rebuild a few seconds, so the Swift phase is the whole cost of an iteration and the Debug arm buys nothing for Swift-side work. **`ZIG_DEBUG=1` is that arm, a SECOND lever rather than something FAST_DEV implies**, because it costs more than it looks like: a Debug engine decodes 2–4× slower (root `../CLAUDE.md` "Building"), so every latency read off that app is fiction — and it is invisible from the running app, which is why the fast-build banner names both configurations — and Zig keys its cache on the optimize mode, so alternating with a release build is a full rebuild each way. Reach for it when the thing you are debugging is Zig-side (safety checks, real panic traces), not while iterating on Swift. It is FAST_DEV-only and refused BY NAME otherwise (`ZIG_DEBUG=1 bash app/build.sh` exits before any build work rather than quietly shipping a Debug engine): FAST_DEV is what stops before notarization and the DMG, so that gate is the entire reason a Debug binary cannot reach an artifact anyone else runs. The trade to know: a resource deleted from `Sources/` lingers in the bundle, so when a fast build behaves strangely, delete `app/MLX Core.app` (or run once without `FAST_DEV`) before believing it. Guard: `tests/test_release_workflow_gates.sh` (the release path still compiles `-c release`, still starts from an empty bundle, the optimize mode defaults to ReleaseFast with the one `-Doptimize=Debug` sitting directly under the ZIG_DEBUG gate behind a refusal that exits before any build work, and the FAST_DEV `exit 0` precedes notarytool/productbuild/create-dmg — the first draft of this change had reindented the script and left `# ... (rest of the block is identical)` where notarization and the App Store .pkg used to be).
- The .app bundles TWO binaries (MLXCore UI + mlx-serve server) — always update together; a stale sibling is the classic "still doesn't work".
- **The bundle's version is STAMPED from the version being released, never copied from the committed plist**: release.yml PlistBuddy's `$CONTENTS/Info.plist` after the `cp` and before `codesign` (stamping the repo file instead breaks the Homebrew step's `git rebase` on a dirty tree). It shipped unstamped once — v26.8.1's DMG contained an app reporting 26.7.12, so `UpdateChecker` offered an update that installing could never satisfy, forever. CalVer's `YY.M` is TZ-pinned in release.yml and app/build.sh together (runners are UTC; an evening release otherwise lands in next month). Guard: `tests/test_release_workflow_gates.sh`; story: `../docs/gotchas/app.md`.
- **An asset dragged out of Finder carries `com.apple.FinderInfo`, and codesign refuses the WHOLE bundle for it** (live 2026-08-09, a screen recording copied off the Desktop): `resource fork, Finder information, or similar detritus not allowed` — reported three minutes into a build, against the BINARY rather than the file that brought the metadata in. build.sh now `xattr -cr`s the staged bundle before signing (fixes the class); `tests/test_resource_xattrs.sh` keeps the checked-in copies clean so it's caught in a second with the file named. It checks ONLY the attributes that actually block signing — `com.apple.macl`/`com.apple.provenance` are added by macOS whenever a sandboxed app touches a file, every existing resource has always carried them, and failing on those would make the guard cry wolf until someone deleted it.
- Agent Sandbox needs `com.apple.security.virtualization` in BOTH signing branches of build.sh (ad-hoc included) or VZ refuses to boot. `swift build` binaries / xctest can't boot VMs; live guard = `SANDBOX_SMOKE=1 <MLXCore binary>`.

## Rules

- **A GUI bundle has NO shell environment, so an env var the user set is INVISIBLE — reading it is not the same as honoring it** (HF cache, 2026-08-14): `huggingFaceRoot` already read `HF_HUB_CACHE` then `$HF_HOME/hub`, but from `ProcessInfo.processInfo.environment`, which a Finder-launched app never carries — so those branches were dead in the shipped app and every install fell through to `~/.cache/huggingface/hub`, listing nothing for anyone who moved the cache off the boot drive (the same reason `hfToken` prefers the token FILE over `HF_TOKEN`, and `CLIInstaller` asks the login shell for PATH). `LoginShellEnv` is the ONE probe now: marker-delimited `printf` through `$SHELL -l -i -c`, 5 s watchdog, cached, primed OFF-main at launch (`refreshHuggingFaceRootFromLoginShell`, rescan only when the root MOVED) so nothing blocks on an rc file; process env WINS over the shell's, and an unset var must not come back as `""` and shadow one the process has. `XDG_CACHE_HOME` was missing outright and is now in both the root and token precedence, matching `huggingface_hub`'s own order (`HF_HUB_CACHE` > `$HF_HOME/hub` > `$XDG_CACHE_HOME/huggingface/hub` > `~/.cache/huggingface/hub`). A CONFIGURED root that is not on disk is nil, never a fall-through to the default cache — the point of the variable is that the models are elsewhere. Gated on `BuildFeatures.customModelFolders`: under MAS an out-of-container cache is unreadable whatever the shell says (audit entry in `HostEscapeAuditTests`). Guards: `HuggingFaceRootTests` + the class scan `testHuggingFaceEnvIsNeverReadStraightFromTheProcessEnvironment`, verified red by injecting one direct read.
- **The app is ONE window: Models / Tasks / Settings / the four media generators are MODES of the chat window** (`Models/ChatWorkspace.swift`), not `Window` scenes. Each has exactly one door on `AppState` (`showModels` / `showTasks` / `showSettings` / `showCreate`) that sets the mode AND bumps `pendingChatOpenTick` — setting the mode alone switches a window nobody is looking at, opening the window alone lands on a transcript. Retired scene ids (`modelBrowser`, `tasks`, `settings`, `imageGen`/`videoGen`/`audioGen`/`model3dGen`) are gone from every surface: `openWindow(id:)` on an unknown id is a silent no-op, so a leftover id is a control that opens nothing (guards: `ChatWorkspaceTests`). The sidebar is a list of DESTINATIONS above the conversations and never rearranges — the row that takes you in is the row that brings you back, which is what the tray/welcome/Tools-menu entries (which arrive already in a pane) depend on.
- **Moving a view into another window means moving its ENVIRONMENT with it** (live crash 2026-08-08): the browser's window injected four objects, the chat window three, and opening the models pane trapped in `ModelBrowserPane.downloads.getter` — SwiftUI reports a missing `@EnvironmentObject` at first RENDER, with no compile error. `testTheChatWindowInjectsEveryObjectItsHostedPanesRead` regex-scans every hosted pane's declarations against an explicit injection map, so a new one fails a test naming the type. Corollary: a pane with its own `NavigationSplitView` (Tasks, Settings, Agents) can't just be dropped in — it needs an `embedded` shell (plain HStack, or promoted to real columns as Tasks was), or it fights the outer sidebar.
- **An environment reader has to BE the column, never produce it** (second crash the same day, and the injection audit was green throughout): the Tasks columns were `TasksView().taskList` / `.taskDetail` — a view VALUE whose computed property is evaluated on the spot. SwiftUI populates `@EnvironmentObject` storage when it INSTALLS a view in the hierarchy, and that instance never was one, so the first click on Tasks trapped in `TasksView.$appState.getter`; the `.environmentObject(…)` chained at the call site cannot save it, because it decorates the view the property already returned, long after the property read the empty box. Columns are `TaskListPane` / `TaskDetailPane`, real types declaring their own environment. The guard is a source scan for `SomeView(…).bareProperty` — a MODIFIER is always a call, so "property access not followed by `(`" separates the two shapes with no allowlist to maintain (comments are stripped first, or it matches the prose warning about it). The window-injection audit is blind to this class by construction: it asks what the window injects, and the bug is WHERE the reading happened.
- **`listRowBackground` is the ROW's backdrop, and `listRowInsets` moves only the CONTENT**: putting the conversation highlight in the former made a selected chat run edge to edge under a column of destinations inset 8pt, while both read the same `SidebarRowStyle` colour — one meaning for gray, two shapes. The fill rides the row content as a plain `.background`, inside the same insets, with `.listRowBackground(Color.clear)` so the list cannot draw a second surface beneath it. Guard: `testTheConversationHighlightIsInsetLikeADestinationRow` (walks back from the fill to the nearest enclosing modifier and demands it be `.background(`).
- **Hiding a window toolbar hides its RESIDENTS** (live 2026-08-09): `.toolbar(.hidden, for: .windowToolbar)` removes the BAR, and the traffic lights and the sidebar-collapse button live in it — a window that cannot be closed, zoomed or collapsed. To retire an empty band, hide its MATERIAL (`.toolbarBackground(.hidden)`), which keeps the bar, its chrome and the safe area it reserves. The older trap pointing the other way (`toolbarBackground(.hidden)` leaves `scrollEdgeEffectStyle` attached to an invisible bar, transcript text clipping mid-line, 2026-07-30) was about the floating CLUSTER; with no cluster nothing floats over the transcript. Guard bans `.toolbar(.hidden)` and requires the material form in both splits.
- **A `ToolbarItem` on macOS 26 draws a capsule around EVERYTHING it holds**: a title beside a button becomes one "Tasks +" lozenge with the title's baseline padding fighting the button's hit area. Ask for `.sharedBackgroundVisibility(.hidden)` (the answer the chat's old cluster used) and let the button carry its own hover-lit target. Static content only — the `»`-eviction rule is about members that appear or change WIDTH at runtime, which a fixed word and one button are not. Shared as `PaneTitleBar` so Tasks and Agents cannot drift.
- **`.listStyle(.sidebar)` adds a horizontal margin that `listRowInsets` does not control** (live 2026-08-09): the same "8" therefore drew two different widths — destinations at the panel edge, conversations pushed ~18pt further in — and zeroing the row insets changed nothing on screen because that was never the number doing the work. No API removes it. Rows that draw their own background, hover, selection and separators get nothing else from a List, so the conversation column is a `ScrollView` + `LazyVStack` taking the SAME `.padding(.horizontal, ChatMetrics.sidebarGutter)` the destination stack takes. One gutter + one row inset constant, read by both halves and the section headers.
- **A row's hit target is whatever its BUTTON covers, not what its fill covers**: sizing the row from an outer frame centres the label in it, leaving a dead strip along the top and bottom of the highlight. The button carries the padding, the height floor and the `contentShape`; a trailing control becomes an overlay (a real Button, hit-tested first) with its space reserved at ALL times, since reserving it on hover reflows the title under the pointer.
- **Exactly one row of the sidebar is lit** (`SidebarSelection`): destinations read `chatWorkspace` and conversations read `activeChatId`, so nothing reconciled them and opening Tasks left the last chat lit beside it — each half correct alone. The active chat is where you ARE only while the window is showing conversations.
- **A placeholder title is a CONCEPT, not a literal** (`ChatSessionTitle`): the auto-titler gated on `title == "New Chat"`, so an agent thread starting as "New agent" would have kept that name forever. Placeholders + the derived title live together; `display(title:hasAgent:)` normalizes at DRAW time so threads stored before agents had a section read correctly without rewriting anything on disk.
- **A view expression can stop the compiler finishing** (live 2026-08-09): the agent editor's identity header as one nested expression took the release build from ~48s to over TEN MINUTES, with no warning — SwiftUI's type-checker just grinds. Split into typed sub-views it was 47.9s. Suspect the last view you wrote when a build time jumps an order of magnitude.
- **A redesign is where affordances disappear quietly** — nothing fails when a control simply stops being drawn. Removing the Agents row's menu once left `startChat(withAgent:)` with NO caller anywhere in the UI while its test stayed green, because the test named the control's location instead of the capability. Pin that it is reachable AT ALL; `AgentsPanelTests` lists every affordance the agent editor had, each named so a failure says WHICH one went.
- **One meaning for gray in the sidebar** (`SidebarRowStyle`): destinations and conversations read the SAME fill for hover/selection. A `List(selection:)` also draws its own tint UNDER `listRowBackground` — that double highlight is why the conversation rows are plain Buttons with no selection binding. Row + delete button are real siblings, never a tap gesture around a button (the swallowed-click class).
- **The chat column has a reading measure** (`ChatMetrics.contentMaxWidth`, 740): transcript, composer and the empty-state greeting all cap at it and centre. One number for all three — a composer even slightly off the answers above it is a seam you can't unsee.
- **The composer never becomes a generator** (create mode REMOVED 2026-08-09): a media chip navigates to the Create pane through `appState.showCreate`, exactly like the Tools menu. Two ways to make an asset, not three: chat with tools on (the model drives at preview settings) or the Create pane (you decide everything). Old sessions may still carry a `createMode` key on disk — the decoder no longer asks for it.
- **Per-chat tool switches SUBTRACT at the resolution chokepoint, never at a turn site** (Tools pill → chevron menu): `AppDefaultsSnapshot.disabledTools` is removed from whatever the agent (or the app defaults) already allowed, so a chat tab can never grant a capability an agent forbids — forbidden rows render disabled rather than offering a switch the resolver would ignore. Turning everything off makes the turn plain chat (`loopRuns`: advertising nothing while still looping is a dead offer). `searchDocuments` is exempt from BOTH the menu and the subtraction — its gate is the attached folder, which is stronger — and `AgentToolKind.chatToggleable` × `AgentToolGroup` are pinned against each other (a tool in no group is unreachable from the UI; one in two renders twice). Stored on the session as RAW STRINGS so a retired tool leaves an unknown name instead of failing the whole session's decode. Guards: `SessionToolDisableTests`.
- **A control the AGENT decides shows the agent's value and says who decided it** (composer Think/Tools/MCP): `AgentResolution` takes `toolsEnabled` from the agent's capabilities and `mcpEnabled` from `capabilities.mcp` and ignores the chat's own toggles — and `AgentCapabilities.web` defaults TRUE, so selecting ANY agent (even one with `tools: false`) forced the tool loop on while the wrench rendered OFF and a click on it wrote a field the resolver discards. `ChatModeToggles.resolve(…, agentLock:)` overlays the agent's values and names the owner PER CONTROL; the disc gets a dashed inset ring (never a dimming — ON/OFF is what its colour has always said) and its menu becomes "Set by \<name\>" + "Edit Agent…", because a locked control that does nothing on click is the dead-control class. Thinking locks ONLY when `agent.enableThinking != nil` — resolution falls back to the surface there, so locking it takes away a control nobody is deciding. The lock is built from `resolvedAgentSettings`, NEVER from `capabilities` directly (a second copy of that rule is how they drifted), and the pre-send intent nudge plus both setters refuse while locked. Guards: `ChatModeTogglesTests`, `ComposerModeControlTests`.
- **The pre-send nudge is ONE pure decision, and tools can be made strictly opt-in** (`ComposerIntent.nudge`): every gate — the opt-in setting, mode already on, agent lock, per-chat "Send Anyway", MCP-before-Agent priority — lives in that one function, and `ChatView.detectIntentPrompt` only gathers its inputs. Settings ▸ Agent Sandbox ▸ "Only use tools when I ask" (`ServerOptions.toolsOnlyWhenAsked`, default OFF = shipped behavior, app-level so it never trips the restart banner) short-circuits it: tools reach the model only where the wrench/MCP disc or the tab's agent turned them on. A second copy of the rule in the view is how one branch would keep nudging — source-scan-pinned in `ComposerModeControlTests`, branch-pinned in `ComposerInputTests`.
- **The chat generates media itself, at PREVIEW settings, one per message** (`generate_image` / `generate_speech` / `generate_music` / `generate_video`): speech and music are separate tools because music IS audio and one overloaded tool makes a 2B guess (`generate_audio` was split — `Agent.renamedTools` maps the old name, since the capability decoder DROPS names it doesn't know and a plain rename would silently strip the capability from every agent that had it). The model picks nothing but the prompt: which model comes from the user's saved settings for that modality, the step/duration knobs from `MediaChatDefaults` (a chat generation blocks chat decode on the one GPU, so it is a preview and the tray window stays the place for full-quality work), and every number it CAN send is clamped in `MediaToolArgs` — a 4B asking for 30 seconds of video is not hypothetical (measured: clamped to 4.0s). Read the spellings models actually emit: asked for "widescreen" a model sends `{"size":"16:9"}`, and an aspect resolves against the user's OWN size (an exact-ratio match escalated a preview to the model's largest 16:9, 8× the pixels). **One generation per USER TURN**, keyed by a turn TOKEN the driver passes rather than a `reset()` it must remember — as a reset call, the headless harness (a second driver on the same engine) inherited a spent budget and silently refused every generation forever. The refusal leads with **"NOT GENERATED"** and the words to relay: with the rule first and the fact second, a refused 4B told the user both items had been made. Music takes the WHOLE knob set the engine reads (`bpm` 30–300 — outside it the server 400s, so it clamps; `keyscale`, `time_signature`, `vocal_language`), each validated against `MusicOptions` — the catalogue IS the accepted grammar — and OMITTED when unrecognised, because only `bpm` is checked server-side and an unknown `keyscale` goes into the conditioning as junk (an absent field is the engine's own "model decides"). Results ride `ChatMessage.media` as a PATH (`ChatMediaRef`) — a 30 s track is tens of MB and `chat-history.json` would carry it forever. An IMAGE carries both: the JPEG bytes the transcript draws AND a `.image` ref for the same Reveal-in-Finder row a track gets, which is why the ref line sits BETWEEN the caption and the data URI (after it, the caption swallows the whole base64) and why both land on ONE message. A missing file is its own row — except for an image, whose picture is still on screen, so the row just disappears. Guards: `MediaToolArgsTests`, `MediaGenProgressTests`, `AgentMediaInlineTests`.
- **A live ETA from observed laps is floored by the MODEL and carries the after-sampling tail** (`H3TimeEstimate.liveEta(floorPerStep:tail:)` from `livePricing` — the pre-run estimate decomposed): under the fast recipe the lap history is dominated by cheap cached steps while the closing steps always refresh at full cost, and the VAE decode never appears in step events — mean × remaining said "77 sec left" with minutes to go. H3 only; LTX keeps the plain mean (uniform laps, no pre-run model). Guards: `H3PlanningTests` floor/tail + decomposition cases.
- **A media generation shows a meter or it reads as a hang**: `ChatTurnEngine.mediaProgress` (ONE value — the inference thread serializes media gen) drives `MediaProgressCard`, determinate when the engine reports a total and indeterminate when it doesn't (TTS length is model-determined, so it sends a growing frame count against total 0 and a bar at 0/0 looks stuck). Elapsed time is a `TimelineView(.periodic)`, never a `repeatForever` animation or a `Timer` — that is the `VoicePulse` tray-wedge class. The four services' identical SSE parsing collapsed into `MediaSSE.classify`; each gained a `generateForAgent(_:server:onProgress:)` that runs the same load → stream → write → unload pipeline WITHOUT touching its pane's `phase`/`task`/`recent`, so a chat generation never hijacks the tray window.
- **"length" is two different endings, and only one of them may CONTINUE the turn** (`TruncationNotice.Cause`, live 2026-08-05): the server reports both a `max_tokens` cap and its own degenerate-tail loop cut as `finish_reason: "length"` — the only OpenAI value for either — so the app told a user with two thirds of their context free that they had hit an output limit neither side set (pi sends no `max_tokens` at all). The cause comes from the server's sibling `finish_details` (`APIClient.truncationCause(fromChoice:)`, static + dictionary-shaped so it is testable without a live stream; ABSENT reads as `.maxTokens`, which is exactly the old behaviour, so an older server or another OpenAI backend is unchanged), and it rides `SSEEvent.truncated(cause)` — renamed from `.maxTokensReached`, which had stopped being true. A repetition loop **ends the turn** (`TruncationNotice.endsTurn`, checked ahead of every recovery branch): the loop's text is already in the transcript, because a streamed delta cannot be retracted and the server's own trim only reaches non-streaming clients, so the next round sends it back as history and the model reads its own loop and resumes — the error-echo class with our transcript as the error, and from the server it looks like five cuts in a row, each firing sooner. A max_tokens cut keeps every existing recovery (chunk-and-retry, truncated-tool-call nudge) — the reply was fine and ran out of room. The loop notice names NO cap: naming one sends people to raise a setting that was never the problem (same rule as `ChatErrorNotice` refusing a diagnosis it cannot support). Guards: `TruncationNoticeTests`. Server side + the measurements: root `## Rules`.
- **The truncation notice is DATA on the message, never content** (`ChatMessage.truncationNotice`, 2026-08-11): the banner used to be APPENDED into `message.content` (`updateLastMessage(content:)`), so both history builders sent "⚠️ Stopped — the model started repeating itself…" back as assistant prose every turn — the error-echo class with our own warning as the error (live capture: the banner rode the muse chat forever). The notice rides `TruncationNotice.Notice` (cause + cap), renders as a footnote under the bubble (`MessageBubble`), and content stays clean by construction; sessions saved by older builds get the in-content banner scrubbed at history build (`TruncationNotice.stripped(from:)`, both builders — markers DERIVE from the legacy `text(...)` so they cannot drift). Decode is tolerant (unknown cause → nil, absent forever on old messages). Guards: `TruncationNoticeTests` data-not-content cases.
- **A failure is its own transcript row, not text appended to the model's answer**: `[Error: …]` glued onto the assistant's own content read as something the model said and gave the user nothing to do. `ChatErrorNotice` classifies it — `.contextOverflow` (the one failure fixable from here) carries the server's real counts and offers "Increase Context Size"; everything else stays `.generic` and shows the server's wording verbatim, because guessing a diagnosis sends people to change settings that were never the problem. The notice message is `failedRetry`, so it renders but is excluded from the history sent back (an error card fed in as assistant output is how a model starts apologising for a server failure). - **A continuation EXTENDS the version being read; the pager counts REGENERATIONS, which a continuation is not** (`AppState.markContinuing` / `finishRevisions`, 2026-08-14): Continue and Regenerate both end at the ONE turn exit, and it could not tell them apart — `finishRevisions` proceeds on `!msg.revisions.isEmpty` alone, so a reply already at 2/2 went to **3/3** the moment you finished it, with 2/3 showing that same reply minus the ending just written.
