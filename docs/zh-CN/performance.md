# 性能与调优

Apple M4 Max，每个引擎使用完全相同的权重。[benchmarks.md](../../benchmarks.md) 逐版本跟踪解码 tok/s，以及当前与其他引擎的正面对比。数字来自 `tests/bench.sh`，它启动服务器并让 [llmprobe](https://github.com/ddalcu/llmprobe) 采集：丢弃预热、三次取中位数，所有人用同一套协议。

![mlx-serve 与 LM Studio · oMLX · MTPLX 对比 —— Gemma 4 + Qwen 3.6，代码补全（M4 Max）](../perf-vs-engines.png)

*代码补全解码 tok/s，v26.8.3，对比 LM Studio 0.4.19+2、oMLX 0.5.2 与 MTPLX 2.5.3：每根柱子都是该引擎的**默认设置** —— llmprobe 测量的是正在运行的服务器，所以不会塌缩成某个“最佳配置”，也没有逐模型调优。四个引擎加载完全相同的 MLX 权重文件。MTPLX 在跑不动的行显示 0（它需要自己的 MTP 工件），LM Studio 在没有对应版本的两行上缺席。解码几何均值：四个共有模型上**比 LM Studio 快 +26%**，全部六个模型上**比 oMLX 快 +25%**，预填充分别为 +36% 与 +10%。真正要紧的两组正面对比发生在对手自己的检查点上：在 oMLX 的 oQ4e（预填充档）上**解码快 +23%**，在 MTPLX 自己的 MTPLX-Optimized 版本上**解码快 +10% / 预填充快 +17%**。*

## 投机解码

四种形态，都等价于贪心（temp=0 时在前 30 个 Token 内逐字节相同；temp > 0 时通过 Leviathan 概率比采样器在数学上精确）：

- **原生 MTP**（Qwen 3.5/3.6/3.8） —— 带已训练多 Token 预测头的检查点（sidecar 或烘焙在内，例如 Qwen 3.8 27B 版本）用模型*自己*的预测头起草，控制器按请求自调深度。支持 MoE sidecar。自动加载，零配置。
- **DFlash 配套草稿模型** —— 模型文件夹可以自带 `drafter/` 块级草稿模型（Muse-Glimmer 版本就有）；服务器随模型一起加载它，切换模型仍保留加速，草稿规模会自适应 Mac。Muse-Glimmer 上约 2 倍。`--no-drafter` 可关掉。
- **PLD**（Prompt Lookup Decoding） —— 与模型无关的 n-gram 匹配，在 `prompt + generated_tokens` 中查找。默认开启，无需逐模型配置。在 Agent 循环、RAG 与代码编辑上胜出，只要答案会回显提示词。
- **Gemma 4 assistant 草稿模型** —— Google 的小型 4 层交叉注意力草稿模型，通过 `--drafter <dir>` 选择性启用。交叉注意力读取目标的 KV cache，因此不会复制权重。

四种形态共用一个**提示词阶段的自适应门控**：3-gram 重复度评分会在新内容上自动关闭投机，于是创意写作与一次性问答以对等速度运行，而不必支付校验开销。一个**运行时接受率门控**会在解码中途、当每次起草的接受率跌破盈亏平衡点时关闭投机，并在该请求剩余部分保持生效。两者都作用于全部四个 API 接口面，流式与非流式，包括带工具的请求。Agent 工具循环是投机解码最好的负载。

## 长上下文

自 v26.8.6 起，滑动窗口模型会把每次注意力读取都裁剪到自己的窗口：提示词块与投机步骤也一样，不只是单 Token 解码。无需开启任何开关。在 M4 Max 上对比 v26.8.5，每个数据点取三次运行的中位数：

| 模型 | | 16k 上下文 | 64k 上下文 |
|---|---|---|---|
| Muse-Glimmer 30B 4-bit | 解码 | 24.7 → **40.2 tok/s** | 8.6 → **21.0 tok/s** |
| Laguna XS 2.1 NVFP4 | 提示词 | 609 → **774 tok/s** | 236 → **540 tok/s** |
| Laguna XS 2.1 NVFP4 | 解码 | 62.7 → **77.7 tok/s** | 34.9 → **46.8 tok/s** |

收益随对话增长；大约 8k 以下还没有什么可裁剪的。

## 调优

默认值已经是快路径。**如果你的 RAM 很充裕，最快的配置就是开箱即用的那个。** 每个与速度相关的旋钮，都是往某个方向做内存换速度的取舍。

| 旋钮（CLI 参数 / 设置） | 默认 | 它对速度做什么 | 什么时候该翻动它…… |
|---|---|---|---|
| **KV cache 量化**（`--kv-quant`） | 关闭 | 2–4K 上下文下解码约 **−10%**；长上下文下融合的打包读取（自 8K 起自动）把代价降到 42K 时约 −18%（此前为 −47%）。省下 2 倍（8-bit）/ 4 倍（4-bit）的 KV RAM。 | ……内存是瓶颈时：16 GB Mac 上的长上下文或大模型。 |
| **PLD**（`--pld`） | 开启 | 在 Agent 循环、代码编辑与 RAG 上收益很大。在新颖文本上会自己关掉。 | 保持开启。只在做同类对比基准测试时用 `--no-pld`。 |
| **采样**（`temperature` / `top_p` / `top_k`） | 模型默认值 | 完整采样相对贪心解码多花约 **6% 解码时间**。 | 跑基准测试时用 temp 0；为聊天质量保留采样。 |
| **连续批处理**（`--max-concurrent`） | 1 | 稠密模型上 4 路并发时 *总* 吞吐约 1.6 倍，代价是一些单请求延迟。 | ……多个客户端共用服务器时。 |
| **前缀缓存**（`--prefix-cache-entries/-mem`） | 开启 | 重复的系统提示词与多轮聊天跳过重复预填充。 | 保持开启。RAM 紧张的 Mac 上限制条目数（应用会自动这么做）。 |
| **原生 MTP**（检查点带 sidecar 时自动） | 开启 | 在代码与编码 Agent 循环上收益很大。 | 保持开启。跑基准测试时用 `--no-mtp`；按请求的 `enable_mtp` 可让 MoE 主干加入。 |
| **草稿模型**（`--drafter`） | 应用中自动 | 在 Gemma 4 稠密代码编辑循环上收益很大（E4B 代码上 +52%，117 → 178 tok/s）。应用会自行下载草稿模型并与稠密 Gemma 4 模型配对；在 CLI 上它仍是选择性启用。 | 保持开启。设置里的开关会关掉自动配对。 |
| **bf16 注意力模型的快速解码**（用 `--no-decode-attn-quant` 关闭） | 开启 | 通过仅用于解码的量化副本提供稠密 bf16 注意力权重：在自带 bf16 注意力的模型上每 Token 耗时减少 23%（poolside Laguna）。预填充仍用稠密权重。在这些模型上输出措辞可能略有差异；量化检查点不受影响。 | ……你希望这类模型的输出与全稠密路径逐字节一致时。 |

从源码构建？**一定要用 `zig build -Doptimize=ReleaseFast`。** 裸跑 `zig build` 会产出 Debug 二进制，慢 2–4 倍，看起来像是性能回退。
