Ship Score: an eval that can't saturate

Give a model one real job. Measure what it cost to finish: memory, time and tokens.

David Dalcu2 Nov 2026M5 Ultra 80c · 256 GB

The idea

Benchmarks die. Every model eventually aces them, and then they stop telling you anything. Tool-call suites, KLD and top-1 are all heading the same way.

Memory and speed never max out. No one will ever say a model uses too little RAM or finishes too fast. So score those.

The rules

  • Pinned prompts. Each one is the same text every run, and scores only compare runs of the same prompt. Seven so far, each rated 1 to 5 for difficulty: a Minecraft-style voxel game, King's Landing with an origami intro, a subway zombie shooter, a Need for Speed-style racer, and three built to stretch even frontier models: flying from a planet's surface to orbit, a real-time strategy skirmish, and a puzzle game of linked doorways.
  • Everything else is your choice. Engine, model, quant, settings and agent. All of it is part of what gets scored.
  • Ship or fail. A run ships when, within 90 minutes of the prompt, npm run build passes, DONE.md exists, and the build passes the play check: it loads without errors, draws something, and responds when you play it. Anything else scores zero. What it got right is the checklist: each prompt ends with a Must have list, and each item earns points.
  • No help. Once a run starts, nobody steps in: no nudges, no answers, no killed tools. The only stop is the 90-minute cap. A run anyone helped doesn't count.
  • Name the inputs. Text only, or text and images. Give the agent what the model supports and say which it was: a model that can look at its own screenshots finishes differently from one that can't.
  • Scored per machine. GPU plus memory, for example M5 Ultra 80c · 256 GB or RTX 5090 · 32 GB.
  • Three runs to publish. One agent run swings too much to stand alone. All three count, so a failed run still pays for what it used.

The score

1,000 × checklist ÷ (√avg GiB × minutes × M tokens)

  • Checklist: the points the game earned on its prompt's checklist, out of 10, as a fraction (8 points is 0.8). Each item is something you can see or do in the game, yes or no.
  • Avg GiB: the engine's memory footprint, averaged over the samples taken between the prompt and the agent's last message. It includes the engine's caches (KV and prompt cache), so their settings count too; on a small model they can outweigh the weights. It counts by its square root: memory matters, but less than getting the game right.
  • Minutes: time from the prompt to the agent's last message.
  • M tokens: millions of tokens the model wrote plus the prompt tokens it had to prefill, from the agent's session log. Prompt-cache hits don't count.

For example, a full checklist in 25 GiB, 40 minutes and 100k tokens scores 50. Miss 2 points and it scores 40. Use four times the memory and it scores 25. Halve the minutes or the tokens and the score doubles.

Minutes charge a slow engine; tokens charge a wordy model. A fast engine can hide a model that writes three times the code it needs, and tokens catch it. Cached prompt tokens are left out because re-reading the context costs a good prompt cache almost nothing, and the minutes already show what it did cost.

Tool calls and errors are reported but not scored. A wasted call already costs its tokens and minutes, a build-and-fix loop is how games ship, and how many calls the same work takes depends on the agent.

Three runs. Add the three runs' checklist fractions (a failed run adds 0) and their costs (√avg GiB × minutes × M tokens, failed runs included). The score is 1,000 × the checklist total ÷ the cost total. One lucky run can't carry a model that fails twice.

Beyond the checklist, the screenshots are the quality signal: every result sheet shows each game, and no taste score goes into the number.

Our results

Every set of runs we make lands here, newest first: one sheet per model family and prompt, with each game's screenshot, its Ship Score and the numbers behind them. Tap a sheet for full size.

Run it

The eval lives in CommunityServe/ship-score: the prompts, the harness that runs, plays and scores a game, the judging rules and the leaderboard, where every submitted game is playable. Point your coding agent at it:

Run the Ship Score eval on my machine against my local model: follow https://github.com/CommunityServe/ship-score/blob/main/AGENTS.md

The agent referees and judges: it asks for your engine and model, starts each run hands-off with the 90-minute cap, judges the checklist from screenshots of the game, and opens a PR with the result. CI recomputes every number from the raw files and merges the PR, and the leaderboard updates. Three runs make an official result; one or two land in previews.

How it's measured

Memory is the engine's physical footprint, sampled every 30 seconds and averaged from the prompt to the agent's last message. Time, tokens and tool calls come from the agent's session log; uncached tokens in are each turn's prompt tokens minus its prompt-cache hits. The play check loads the build in headless Chromium, starts it, presses keys, moves the mouse and clicks, and looks for errors, a blank screen or a screen that never changes. Each run starts with a fresh server and an empty folder.

The checklist is the prompt's own Must have list, so the model knows exactly what earns points. Each item is something you can see or do, worth 1 to 3 points, 10 in all; the points are published here, not in the prompt, so the model builds the whole list. The things that make the game work at all weigh most. Whoever ticks it plays the game and answers yes or no, never "mostly".

Difficulty is how much has to work at once and how hard the hardest part is: 1 is one system built from well-known techniques, 5 is several hard systems that all have to work together (rendering tricks, simulation, AI, precision), hard even for a frontier model. Scores only compare runs of the same prompt, so difficulty tells you what a score was earned on, not how to scale it.
