Ship Score: an eval that can't saturate

Give a model one real job. Measure what it cost to finish: memory, time and tool calls.

David Dalcu2 Nov 2026M5 Ultra 80c · 256 GB

The idea

Benchmarks die. Every model eventually aces them, and then they stop telling you anything. Tool-call suites, KLD and top-1 are all heading the same way.

Memory and speed never max out. No one will ever say a model uses too little RAM or finishes too fast. So score those.

The rules

  • Pinned prompts. Each one is the same text every run, and scores only compare runs of the same prompt. Seven so far, each rated 1 to 5 for difficulty: a Minecraft-style voxel game, King's Landing with an origami intro, a subway zombie shooter, a Need for Speed-style racer, and three built to stretch even frontier models: flying from a planet's surface to orbit, a real-time strategy skirmish, and a puzzle game of linked doorways.
  • Everything else is your choice. Engine, model, quant, settings and agent. All of it is part of what gets scored.
  • Ship or fail. A run ships when, within 90 minutes of the prompt, npm run build passes, DONE.md exists and the build passes the play check: it loads without errors, draws something, and responds when you play it. Anything else scores zero. The play check catches builds that don't run; whether the result is what was asked stays with the reviewer.
  • No help. Once a run starts, nobody steps in: no nudges, no answers, no killed tools. The only stop is the 90-minute cap. A run anyone helped doesn't count.
  • Name the inputs. Text only, or text and images. Give the agent what the model supports and say which it was: a model that can look at its own screenshots finishes differently from one that can't.
  • Scored per machine. GPU plus memory, for example M5 Ultra 80c · 256 GB or RTX 5090 · 32 GB.
  • Three runs to publish. One agent run swings too much to stand alone. Runs are averaged, and a fail counts as zero.

The score

10,000,000 ÷ (avg GiB × minutes × (tool calls + errors))

  • Avg GiB: the engine's memory footprint, averaged over the samples taken between the prompt and the agent's last message. It includes the engine's caches (KV and prompt cache), so their settings count too; on a small model they can outweigh the weights.
  • Minutes: time from the prompt to the agent's last message.
  • Tool calls: fewer is better. Weak models repeat the same call over and over.
  • Errors: calls that came back as an error. The bar is zero, and each one counts again on top of its call.

Halve any one of them and the score doubles. For example, 40 GiB, 40 minutes and 100 clean calls scores 62.5. The same run in 20 GiB scores 125.

Tokens aren't in the formula on purpose. Every token, written or read, already costs minutes, and a fast engine or a good prompt cache shouldn't be charged for work the clock says it did quickly.

A reviewer can also give an optional 0–10 for how close the result came to what was asked. It's shown next to the score, never mixed into it.

The referee prompt
Run the Ship Score eval (https://mlxserve.com/blog/ship-score/) on this machine against my local model. You are the referee, not a player: never write, fix or hint at the game's code. Only my local model works on the game. Once a run starts, don't touch it: no nudges, no answers, no killed tools. The only stop is the 90-minute cap, and a run anyone helped is void. Ask me for anything below I haven't given you: - My local engine: its OpenAI-compatible base URL, the model id, and the engine's process (name or PID). - The agent harness to run it with (for example pi or opencode), pointed at that model. Steps: 1. Record the rig: chip or GPU, GPU cores, total memory, engine and version, model and quant, harness and version, and the inputs the harness gives the model (text only, or text and images). Give it images if the model supports them. 2. Make a new empty folder. Save the game prompt below to prompt.txt exactly as given, ending with one newline. Check its sha256 against the one published on the page, and stop if it differs. 3. Start a memory sampler: every 30 seconds, append a timestamp and the engine process's memory footprint (macOS: phys_footprint from `footprint -p PID`; NVIDIA: the process's VRAM from nvidia-smi plus its host RSS) to mem.txt. 4. Start the harness in that folder, non-interactively, with prompt.txt as the only message. Note the start time. Stop it if it runs past 90 minutes. 5. When it ends, stop the sampler and work out: - minutes: from the prompt to the agent's last message - avg GiB: the average of the samples taken between the prompt and the agent's last message - tool calls, and tool errors (calls whose result was an error), from the harness's session log - tokens out and in, and decode and prefill speeds if the engine logs them 6. The play check: serve the build (`npx vite preview`) and load it in headless Chromium with Playwright, recording page errors. Screenshot it after it loads. Click to start (a visible Play, Start or Enter button if there is one, else the centre of the page), press a number key, hold W for a second, move the mouse, left click and right click, with a screenshot after each. It passes when there are no page errors, the first screenshot isn't blank and at least one input changed the screen. 7. The ship gate: within 90 minutes, `npm run build` passes in the folder, DONE.md exists and the play check passes. Otherwise the score is 0. 8. Score = 10,000,000 ÷ (avg GiB × minutes × (tool calls + errors)). 9. Report one row: rig, inputs, engine, model, harness, prompt name, avg GiB, time (m:ss), calls (errors), tokens out / in, play check, score, and the folder path. 10. Do three runs: repeat from step 2 in a new folder each time, and ask me to restart the engine between runs. Report each row and the average score (a fail counts as 0). Then open the games for me and ask for my optional 0–10 reviewer score. The game prompt: <paste one of the prompts here>

How it's measured

Memory is the engine's physical footprint, sampled every 30 seconds and averaged from the prompt to the agent's last message. Time and tool calls come from the agent's session log. The play check loads the build in headless Chromium, starts it, presses keys, moves the mouse and clicks, and looks for errors, a blank screen or a screen that never changes. Each run starts with a fresh server and an empty folder.

Difficulty is how much has to work at once and how hard the hardest part is: 1 is one system built from well-known techniques, 5 is several hard systems that all have to work together (rendering tricks, simulation, AI, precision), hard even for a frontier model. Scores only compare runs of the same prompt, so difficulty tells you what a score was earned on, not how to scale it.

Build a first-person voxel sandbox game for the browser with three.js, in the current directory. Look at the screenshots yourself and fix whatever looks wrong. - `npm run build` must pass. Write README.md (what it is, controls) and DONE.md (what you built, what you checked, what you would improve next). - Work autonomously to the end; do not stop to ask questions.
